# SVG composition, export, and collection integration

## Find and embed the actual icons

Read `manifest.json` and use each entry's `files[style]` path relative to the collection root. Current styles are `stroke`, `two-tone`, `duotone`, `fill`, and `color`; prefer the manifest when this changes. Search metadata rather than a copied catalog. Brand marks retain their source terms in `BRAND-REFERENCES.md` and `vendor/brand-logos/` when distributing a diagram outside this repository.

Existing examples are generated by:

- `scripts/diagram.mjs`: simple architecture and six-stage loop.
- `scripts/deep-agent-diagram.mjs`: a larger, source-grounded research architecture.

Reuse their embedding approach: copy each used SVG's native geometry into a `<symbol>` in the diagram's `<defs>`, retain the source `viewBox`, and place it with internal `<use href="#diagram-icon-agent">` references. Include each distinct symbol once. Preserve inherited `fill`, rounded line caps, and joins when removing the outer SVG element. Keep icon proportions with a square viewport; do not rescale axes independently.

The current library's icon SVGs are deliberately simple native paths and circles. If inputs later contain IDs or definitions, namespace the copied IDs and rewrite their references instead of creating duplicate IDs. Escape XML labels and attributes. Give the diagram's title, description, markers, and symbols unique names, especially when it may be embedded inline with another diagram.

The deliverable should be a self-contained SVG with `xmlns`, explicit dimensions and `viewBox`, `role="img"`, `aria-labelledby`, `<title>`, and `<desc>`. Use native text and paths, internal symbols, and system font fallbacks. Do not depend on external `<image>` URLs, fonts, JavaScript, CSS files, or `foreignObject`; those can fail in Markdown viewers or exported images.

## Readable geometry

Preserve the collection's flat, clean styling: rounded cards, restrained neutral surfaces, and style-appropriate accents. Keep equal icon sizes for peers, generous margins, and labels that distinguish concepts without relying on logos alone. Connector arrowheads must stop at node boundaries, not inside icons. Route feedback and error paths separately from forward flow, and label ambiguous edges.

SVG text does not wrap automatically. Use separate `<text>` elements or explicit `<tspan>` lines with measured spacing. Check the full image and its expected display size. A large canvas may require splitting sections or enlarging essential labels to remain legible in a README. Canvas dimensions are a layout choice, not a required 1600 px template.

## Editable generation and output paths

For a new collection diagram, add a focused generator under `scripts/` or extend a suitable existing generator. Accept the collection root as an argument, resolve icon paths from that root, and return the written SVG paths. Connect the generator to `scripts/build.mjs` only when the task includes collection integration. Avoid silently using the script's own directory when a caller has supplied another root.

For another project's diagram, keep its source and assets in that project's requested destination. A generator can accept separate `collectionRoot` and `outputDir` arguments. Do not modify upstream icon sources, manifests, README files, or the ZIP merely to consume the collection.

## Rendering and export

The collection's renderer uses the SVG dimensions by default. Run it from the collection root, or address the script and input/output files with absolute paths:

```sh
node scripts/render-svg.mjs examples/diagrams/color/example.svg --out examples/diagrams/color/example.png
node scripts/render-svg.mjs examples/diagrams/color/example.svg --out /tmp/example-readme.png --width 960
```

Replace example paths with the actual generated file. Read the renderer's usage or declared dependencies if it reports a missing rendering dependency; no separate installed anatomy skill is required. `--scale` changes raster density while `--width` sets the rendered width. Inspect the PNG visually before delivery; correct the source and regenerate when necessary.

Check that the SVG parses, IDs are unique, and every `href="#…"`, `url(#…)`, and accessibility ID reference resolves. Confirm all intended nodes, forward/return edges, and exits are present. `npm run check` validates the icon collection; it does not replace diagram-specific reference and visual checks.

## README and package integration

For collection documentation, edit `README.md`, the Color source. `scripts/readmes.mjs` generates `README-stroke.md`, `README-two-tone.md`, `README-duotone.md`, and `README-fill.md`; it substitutes `examples/diagrams/color/` paths with each style. A new example integrated across styles therefore needs matching output filenames in all five directories. Preserve the shared brand header, style navigation, and five-style comparison block.

After editing the generator and Color README, run `npm run build` and `npm run check`. Render or refresh PNGs separately; the build does not regenerate them. Confirm that every README link resolves to the matching style. If updating the distributable is in scope, run `npm run pack` after all SVGs, PNGs, source files, and docs are current, then verify its entries match the delivered files.

Use relative Markdown paths from the receiving document's directory:

```markdown
![Agent tool loop with result feedback and a final-response exit.](assets/agent-tool-loop.svg)
```

Choose the SVG for crisp documentation and the PNG where the host requires a raster image. The SVG can embed the icon collection without separately shipping all original icon files because its symbols contain their paths.
